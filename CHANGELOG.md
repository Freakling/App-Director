# Changelog

Each entry lists what changed. **Upgrade steps** at the end of an entry cover both framework fixes and app-owned file updates (AGENTS.md, TASKS.md, product/brief.md), so every project reaches the same capability level after upgrading. Onboarding carries them out; the fast upgrade mode runs only these steps, and the full mode also re-checks everything as if newly installed.

## 1.12.0 (2026-10-29)

- **The settings template allows no generic code runner.** `.claude/settings.json` no longer allows `npm`, `npx`, `pnpm`, `yarn`, `flutter`, `python` and `pip` with any arguments. A prompt injected from a fetched page could run `python -c` or `npx <package>` without a prompt and push or read credentials, so those runners now ask first, and so does any other stack command the agent runs directly, such as a release build, a deploy or an install. The allow list keeps the framework's own scripts (`bash tools/...` and `node tools/ui/...`), git, and the web search and fetch the researcher uses. A command that `tools/check.sh` or `tools/security.sh` runs itself needs no allow rule, because the allowed script runs it. `selftest.sh` fails when the template allows a generic runner, or every command, with a wildcard.
  - **Upgrade steps:** `.claude/settings.json` is framework-owned and arrives with the upgrade, which replaces the old allow list (if you edited the file, merge its `.adir-new` file). A stack command you want to run without a prompt goes in your own `.claude/settings.local.json`, written as that exact command, for example `"Bash(flutter test)"`. Restart Claude Code so the new list loads.
- **The installer now git-ignores `.claude/settings.local.json`, as the README says.** `*.local` matches only names that end in `.local`, so it never reached `.claude/settings.local.json`, the personal settings file that holds each machine's permissions and shouldn't be committed. The installer now adds `/.claude/settings.local.json` to `.gitignore`. `*.local` stays, because it covers `.env.local`.
  - **Upgrade steps:** the upgrade adds `/.claude/settings.local.json` to your `.gitignore` when it's missing, under your `# App Director` heading (the installer writes one at the end when there's none), and keeps the lines already there. Nothing else changes. Check it with `git check-ignore -v .claude/settings.local.json`. A copy of that file that's already committed stays tracked until you run `git rm --cached .claude/settings.local.json`.
- **An upgrade adds a missing `.gitignore` line under the existing `# App Director` heading.** The installer wrote its heading again at the end of the file whenever an upgrade added a line, so `.gitignore` could end with a second copy. An added line now goes directly after the last line of the block under the heading the file already has, and the heading is written, with the lines, only when the file has none. `.gitattributes` gets the same fix, since the installer fills it the same way. The selftest checks that one heading remains in each file.
  - **Upgrade steps:** none; the installer arrives with the upgrade.
- **The screen-capture tooling pins Playwright to one exact version.** `tools/ui/package.json`, and the selftest's copy of it, asked for `^1.50.0`, so an install took the newest Playwright in that range, and with it the Chromium that `npx playwright install chromium` downloads. They now pin `1.64.1`. Playwright pins its only dependency, `playwright-core`, to the same version, and that package has no dependencies of its own, so the installed tree is fixed without a lock file; `tools/ui/.npmrc` says why there is none. `selftest.sh` fails when either manifest asks for a range.
  - **Upgrade steps:** none; the files are framework-owned and arrive with the upgrade. An app that installed the capture tools earlier keeps the Playwright it installed until it runs `cd tools/ui && npm install` again, which installs the pin.
- **The screen-capture tooling asks for Node 20, as Playwright does.** Playwright 1.64.1 declares `node >=20`, but `tools/ui/package.json` and `tools/ui_capture.sh` asked for Node 18, so a Node 18 machine passed the check and then failed the install. They now ask for Node 20 or newer, and the capture's message, the `ui-design` procedure, the onboarding and the selftest say so too, and the selftest refuses a Node 19. The check never needs Node.
  - **Upgrade steps:** an app on Node 18 or 19 installs Node 20 or newer before it captures, from nodejs.org or its version manager. Nothing else changes: the files are framework-owned and arrive with the upgrade, and the check never needs Node.

## 1.11.0 (2026-10-25)

- **The OWASP baseline is the Top 10:2025.** `rules.md`, the checklist (`.app-director/reference/owasp.md`), the procedures, the messages of `tools/check.sh` and `tools/security.sh` and the self-test fixture notes use the OWASP Top 10 (2025) in place of the 2021 edition; the API Security Top 10 stays at 2023. Server-Side Request Forgery is now part of Broken Access Control, so its checks sit under A01. Vulnerable and Outdated Components becomes Software Supply Chain Failures and widens to what an agent can check in a repository: a committed lock file, pinned versions, known package sources, and CI and build files that install only from them, next to the dependency audit. New is Mishandling of Exceptional Conditions (A10): errors that leak internals to users, failing open on an exception in an authorization or validation path, swallowed errors and unhandled rejections, and resource cleanup on the error path. `tools/security.sh` labels dependency findings A03:2025 Software Supply Chain Failures.
  - **Upgrade steps:** the rules, procedures, checklist and tools are framework-owned and replaced by the upgrade. A project that names a 2021 category in a `product/decisions.md` deviation or in a bug item's title can re-label it with this table:

    | 2021 | 2025 |
    |---|---|
    | A01 Broken Access Control | A01 Broken Access Control |
    | A02 Cryptographic Failures | A04 Cryptographic Failures |
    | A03 Injection | A05 Injection |
    | A04 Insecure Design | A06 Insecure Design |
    | A05 Security Misconfiguration | A02 Security Misconfiguration |
    | A06 Vulnerable and Outdated Components | A03 Software Supply Chain Failures (an expansion of it) |
    | A07 Identification and Authentication Failures | A07 Authentication Failures (renamed) |
    | A08 Software and Data Integrity Failures | A08 Software or Data Integrity Failures |
    | A09 Security Logging and Monitoring Failures | A09 Security Logging and Alerting Failures (renamed) |
    | A10 Server-Side Request Forgery | A01 Broken Access Control (merged in) |
    | (none) | A10 Mishandling of Exceptional Conditions (new) |
- **The OWASP Top 10 is a non-negotiable baseline.** `rules.md` makes the OWASP Top 10, and the OWASP API Security Top 10 for anything that serves an API, a baseline every app meets. It is framework-owned: no project setting turns it off, and a deviation is only an accepted line in `product/decisions.md` that names the OWASP item and why. `design.md` has each option state its effect on the baseline where it touches security. `review.md` gets a step that checks each change touching input, authentication, authorization, sessions, secrets, data access, file or network access, or dependencies against it and reports the OWASP item; a deviation without an accepted decision is a finding. The check's secrets and UI purity messages say which OWASP category they serve, without claiming to cover the baseline. Onboarding tells the human it exists.
  - **Upgrade steps:** none; the rules, procedures and `tools/check.sh` are framework-owned and replaced by the upgrade.
- **New: `/security`, a recurring security assessment against the OWASP baseline** (`.app-director/procedures/security.md`). It validates what is built, not only each change. First the tools, through the new `bash tools/security.sh`: the dependency audit for the manifests it finds (`npm audit --omit=dev`, `pnpm audit --prod` or yarn's audit, `pip-audit` (only on a `requirements.txt` with every package pinned by `==`, read with `--disable-pip --no-deps` so nothing is installed or built), `dotnet list <solution or project> package --vulnerable --include-transitive`, and `flutter pub outdated` as information only), the check's secrets scan and UI purity step, and Semgrep with `p/owasp-top-ten` when it's installed. A tool that isn't installed, or can't reach its service, is skipped with a note, and nothing is installed without asking (Corepack may not download yarn or pnpm). Semgrep's findings keep only file, line, column and rule, so no matched source is copied. Then the `reviewer` reads the app in a fresh context through the new checklist, `.app-director/reference/owasp.md`: each OWASP Top 10 (2021) and API Security Top 10 (2023) category broken into checks marked code, config or people, paraphrasing OWASP ASVS 5.0 level 1 where it applies, with where to look for each stack. Each finding gets its OWASP item, a severity (high, med, low, with a rubric), the evidence by file and line and a proposed fix, and becomes a bug item in TASKS.md, high severity first. What only people can do (access reviews, incident response and who is on call, key rotation, multi-factor authentication, the security officer's sign-off) goes to the director as a list, and the items they agree to become human items. The report goes to `product/security/YYYY-MM-DD.md`: the commit, what ran and what was skipped and why, a line per category (verified, findings, not checkable here, or not applicable), and what a clean run doesn't prove; a category is never marked verified from a tool passing alone. It runs on request; before a release is proposed when something was built since the last report or there is none (`release.md`; whether it ran or not, an open high bug item naming an OWASP item blocks the release unless `product/decisions.md` accepts a deviation for that item); and when `/next-task` finds one due and the human agrees: `bash tools/security.sh --due` counts the built items (squash merges included) since the newest report against `tools/check.cfg` › `[security] every` (10 by default), and with no report yet it is due. The selftest runs the tool step on a seeded vulnerable fixture and its clean twin in `tests/security/`; `tests/security/README.md` is the manual check for the reviewer pass.
  - **Upgrade steps:** the procedures, the checklist, the skill, the reviewer, `settings.json` (it allows `bash tools/security.sh` and `bash tools/security.sh --due`) and `tools/security.sh` are framework-owned and arrive with the upgrade. `tools/check.cfg` is project-owned and kept: with no `[security]` section the default of 10 applies. To set it, add `[security]` and `every = 10` (the seed has them, with a comment).
- **The security assessment never quotes a secret, and names the OWASP editions it checks.** Evidence, the report and bug items name a secret only by `file:line` and its kind, never its value or the line that holds it (`security.md` has the rule). A tool counts as clean only when it exits 0 with its nothing-found output: a timeout (exit 124), a network or restore error, or a scan that failed is "couldn't run", with its reason (`tools/security.sh`). `owasp.md` and `rules.md` name the OWASP Top 10 (2021) and the API Security Top 10 (2023), and `release.md` runs the assessment on `main` at the release commit, not on a detached tag checkout.
  - **Upgrade steps:** none; the procedures, the checklist, `rules.md` and `tools/security.sh` are framework-owned and replaced by the upgrade.

## 1.10.0 (2026-10-25)

- **The command guard blocks commands that hang, and the check limits its test runs.** `guard-commands.sh` (also run for Monitor) now blocks, with a message that says why and gives the form that works: Python reading `-` from an empty heredoc (the "is Python here?" probe; on Windows it waits for console input and never returns; use `python3 --version`), an `until` or `while` loop with `sleep` that isn't under `timeout N` of 280 seconds or less, a loop that reads a background command's `tasks/<id>.output` without waiting for the `exited with code` or `[killed]` line Claude Code appends, and a lone `sleep` over 280 seconds. The 280-second limit keeps a wait inside the five-minute prompt cache, so the next turn doesn't rewrite the whole context. The guard still starts no other processes. `rules.md` says to give every command that may run long a limit under five minutes and to start a long check with `run_in_background`. `tools/check.sh` runs the stack check and `tools/check.local.sh` under GNU `timeout` (or `gtimeout`) for `[tests] timeout` seconds from `tools/check.cfg` (default 600; `CHECK_TIMEOUT` overrides it); a run that hits the limit exits 3 and says so, unless a failure was already seen, which exits 1. Without GNU timeout the check notes it and runs without a limit.
  - **Upgrade steps:** the hooks, `settings.json` (the guard's matcher is now `Bash|Monitor`), `rules.md` and `tools/check.sh` are framework-owned and replaced by the upgrade. `tools/check.cfg` is project-owned and kept: with no `[tests]` section the default of 600 seconds applies. To set the limit, add `[tests]` and `timeout = 600` (the seed has them, with a comment).
- **Drawings in `director/ui/` don't fail the secrets check.** Each Excalidraw drawing embeds its screenshot as base64 in its JSON, and random base64 can match a generic key rule. The seed `.gitleaks.toml` now allowlists `director/ui/*.excalidraw` by path (drawings directly in that folder only). A credential in any other file still fails the check and the pre-commit hook.
  - **Upgrade steps:** `.gitleaks.toml` is project-owned and kept on upgrade, so add the allowlist to it: uncomment the `# [allowlist]` block if it has one, or, if it already has an active `[allowlist]` table, add only the entry `'''^director[\\/]ui[\\/][^\\/]*\.excalidraw$'''` to its `paths` (a TOML table can't appear twice). The seed's comment gives the entry. Then run `bash tools/check.sh --architecture`.

## 1.9.0 (2026-10-25)

- **A screen is re-arranged by dragging its grey boxes.** The starter drawing's grey numbered boxes are no longer locked. Drag or resize one and the reader takes it as a blue `keep` box for that element, named after it, at its new place, with any keys typed into it, marked `"from": "existing"` with the element's number `n` in `drawing.json`. Each grey box records the rectangle it was drawn at and is compared with that (within 2 pixels), so a recapture doesn't turn untouched boxes into moves. Untouched, deleted, hidden or locked boxes and boxes from an older starter are ignored, as are the number labels. With no element map, or when it no longer has the element, a moved grey box is skipped with a note; one dragged outside the frame is reported; an element claimed twice (moved grey box, blue box, red X) gets a note. A new blue box named after the element still works. The legend, `product/ui/README.md` and the procedure say so. The shared reader fixtures are at Godot Director 4.3.0, and Godot's reader output matches this reader byte for byte.
- **The screen-design README is organised by feature.** `product/ui/README.md` now follows the order of Godot Director's: the workflow, what a capture gives you, boxes, colours, containment, patch or replace, re-arranging a screen, other states and sizes, processing and verifying, Excalidraw and the files table. It also names the capture setup (Node 18 or newer, the catalog in `tools/ui/screens.mjs`, `tools/ui_capture.cfg`). Re-arranging a screen is covered by the entry above.

**Upgrade steps:**
1. `product/ui/README.md` is an app-owned seed the installer leaves alone. Replace it with the source's `project/product/ui/README.md`, carrying over any notes you added.
2. Recapture the screens so the starters are regenerated unlocked.

## 1.8.0 (2026-10-23)

- **New: `/ui-design`, screens you design by drawing** (`.app-director/procedures/ui-design.md`). The agent sees your web app's screens as a user does, layout bugs that tests can't see are caught, and you redesign a screen by drawing boxes over its screenshot instead of describing a layout. The workflow is the one Godot Director pilots, with a capture adapter for web apps: the same drawing conventions, the same `drawing.json`, the same screen spec, and the same element map and lint rules.
  - **Capture runs Node and Playwright, kept apart from the app.** `bash tools/ui_capture.sh [<screen>|--all]` opens the app on this machine in headless Chromium (no display needed) and writes to the gitignored `product/ui/captures/`, per screen, state and size in `tools/ui_capture.cfg`: the screenshot (`.png`), the element map (`.elements.json`: every visible element that is focusable, has text, has a meaningful role and a name, or has a `data-testid`, with its role and accessible name from the accessibility tree, its pixel and percent rect, Tab order, overflow and the size its content needs), the screenshot with every element outlined and numbered (`.map.png`), the layout lint (`.lint.txt`) and a starter drawing for the default state at the default size. `--state` narrows it, `--size` captures one size, `--list` prints the catalog and `--missing` lists the screen files in the UI folders that the catalog doesn't cover (it never fails). Exit codes as the check: 0, 1 when a screen fails (a page error is put at the top of its lint file, a page that reloads while it is mapped fails only its screen, and the run goes on), 3 when it can't run. Capturing one screen, a problem in another catalog entry is noted, not a failure. The tools are plain ES modules in `tools/ui/` with their own `package.json` (Playwright, Node 18 or newer, no lockfile); install them once with `cd tools/ui && npm install && npx playwright install chromium`. Capture never installs anything, and the check never needs Node.
  - **Only this machine, never real user data.** Capture opens `tools/ui_capture.cfg` › `[web] base_url` and refuses any host but `localhost`, `127.0.0.1` and the hosts in `[web] allow_hosts`, so it never opens a deployed site. Every request and WebSocket a page makes goes through the same check: one to another host is blocked and noted in the screen's lint file (`note: blocked requests to <host>`), redirects are followed only while they stay on this machine, and the `api` helper follows none. A dev server whose page calls a hosted backend is captured without that backend's data. `[web] start_command` starts the app when nothing answers, with its output in `.app-director/state/ui_app.log`, and capture stops it afterwards, also when it is interrupted; an app a killed capture left running is stopped by the next capture before it looks for a running one. Each screen and state gets a fresh browser context; a state seeds its data through the app's public API with the `api` helper it is given (requests that are refused for a host that isn't local), and a screen that needs a sign-in uses a test account's saved state in the gitignored `tools/ui/.auth/`.
  - **Captures repeat.** Animations and transitions are stopped, the clock is fixed, `Math.random` is seeded, the locale and time zone are fixed, and capture waits for the page to load, the fonts and the network, then `settle_frames` animation frames. Two captures of the same state and size on the same machine, with the same Playwright install, give the same files. Playwright isn't pinned (`^1.50.0`, no lockfile), so after `npm install` brings a newer Playwright and Chromium, captures can differ from earlier ones.
  - **The catalog** (`tools/ui/screens.mjs`, project-owned) lists every screen: its id, title, route and optional states, sign-in, source file and `animate` opt-out. Unknown keys, duplicate ids, a missing title or a route that isn't a path are named. A new app's seed lists the root route.
  - **The lint** has the seven rules of the other frameworks, read for the web: `squeezed-text`, `stretched-control`, `off-screen` (sideways, or out of an `overflow: hidden` parent; below the fold and content a parent scrolls are fine), `overlap` (the upper sibling takes the clicks), `unreachable` (Tab never gets there, including everything after a focus trap; what an open modal dialog covers is fine), `no-default-focus` (an open dialog without the focus) and `hard-coded-position` (a warning). It runs in capture, verify and the build's Screens step, never in `bash tools/check.sh`, which needs no browser and no running app. Findings never change capture's exit code.
  - **`process`** reads your drawing through `tools/ui/drawing.mjs`, a port of Godot Director's reader that gives the same `drawing.json` for the same drawing (32-bit geometry, the same rounding and the same JSON text), briefs you element by element, settles each open point with options and a recommendation, and records the spec `product/ui/<screen>.md`, a decisions line per decision, the brief only if the screen's behaviour changed, and one item per screen with the new optional `UI:` field. It needs Node, not Playwright.
  - **`verify`**: `bash tools/ui_capture.sh <screen> --verify` captures the screen, then prints one row per element of the spec's Layout table (present by `data-testid`, where within `[verify] tolerance_pct`, reachable by Tab, lint-clean), the `data-testid` elements the spec doesn't list, lint in the screen's other states and sizes, and drawn boxes whose element has moved; with a processed drawing it writes `<screen>.compare@<W>x<H>.png`, your drawing's screenshot beside the new capture with the drawing's boxes outlined by intent. `tools/ui/overlay.mjs` draws the map and compare images in Chromium.
  - **Apps without a web UI.** A native Flutter, mobile or desktop app leaves `[web] base_url` empty: capture exits 3 with "capture isn't available for this app yet", while `list` and `process` work, and `--verify` checks that each name in the spec is in the source and exits 3, so the item's `(check)` outcome is reported as unverified.
  - **The workflow uses the spec.** `build.md` has a Screens step for an item with `UI:` (read the spec and `drawing.json`, build with flex or grid, give the elements their `data-testid`, keep the catalog entry current, run `--verify`, report a `Screen:` line). `review.md` checks the item against the spec, the compare image and the lint output. `acceptance.md` regenerates the compare images and asks you to judge the screen against your drawing. `align.md` lists screens the catalog doesn't cover, spec names missing from the source, drawings changed since they were processed, and `UI:` fields pointing nowhere. `design.md` sends layout questions to `/ui-design`. `rules.md` names the procedure, where each screen's layout and your drawings live (`director/ui/`, read-only for the agent), and asks for a catalog entry per screen and a `data-testid` per element a spec names. `tasks.md` describes `UI:`.
  - **Onboarding and the docs.** Onboarding asks for the app's dev server address (`[web] base_url`) and offers the Playwright install. The ownership interview asks once whether you want to design screens by drawing (`UI / screen layout` becomes `director designs (director/ui/), agent builds`, and `director/ui/` is offered); declining changes nothing else. The AGENTS.md template's Layout lists `product/ui/` and `tools/ui/`, and the README lists `/ui-design` and the installed files. The installer adds `/product/ui/captures/`, `/tools/ui/node_modules/` and `/tools/ui/.auth/` to `.gitignore` and `/tools/ui/** text eol=lf` to `.gitattributes`; `.claude/settings.json` allows `bash tools/ui_capture.sh` and the framework's own `node tools/ui/drawing.mjs`, `overlay.mjs`, `verify.mjs` and `capture.mjs`.
  - **The starter drawing says how to open and save it.** The capture step gives one plain message: nothing to install, excalidraw.com in the browser with no account, how to open the starter (the menu's Open, or drag it in), how to save it as `director/ui/<screen>.excalidraw` (Save to… in Chrome and Edge, which let you pick the folder; other browsers save to Downloads, so move and rename the file), that the drawing stays on the machine unless Live collaboration or a shareable link is used, and "tell me when it's saved". The drawing guide (`product/ui/README.md`) gets a "Using Excalidraw" section with the same facts, plus the address-bar install.
  - **Selftest** checks the wiring and the install; reads the reader fixtures shared with Godot Director (`tests/ui-drawing/README.md` names the release they came from) (a green box with bound text and `click:`, a blue box over an existing element, a red X, an arrowed comment, a nested box, a note outside the frame and a freehand squiggle) into the expected `drawing.json` and into exactly the text Godot Director's reader writes, the same drawing with the image moved and scaled to 50% into the same percentages, and the starter into the hand-checked fixture, valid Excalidraw that reads back empty. With Playwright installed (in `tests/ui-web/node_modules`, or `ADIR_PLAYWRIGHT`), it captures a fixture web app served on this machine: every file per screen, state and size, the same element map twice, each lint rule on a page built to break it and none on a clean page, a known Tab order with one trap and exactly one unreachable element, verify with no deviation and with one element moved 10%, a page error, a missing route and a page that reloads while it is mapped failing only their screen, a refused host, requests, a redirect and a WebSocket to other hosts blocked and noted while the page's own requests go through, the `api` helper refusing a redirect, a modal dialog and a scrolled carousel giving no findings, a broken catalog entry not stopping verify of another screen, the app started and stopped by `start_command`, and an app left by a killed capture stopped by the next one. Without Playwright those tests are skipped. It also checks that capture exits 3 without Node, Playwright or a web app and writes nothing, and that the check passes without them.

**Upgrade steps:**
1. The installer creates `tools/ui/screens.mjs`, `tools/ui_capture.cfg` and `product/ui/README.md` when the app doesn't have them, and adds the `.gitignore` and `.gitattributes` lines; check that they're there, and commit the three files. An existing `product/ui/README.md` is the app's own and stays as it is; the capture step's message gives the same instructions.
2. If the app has a web UI, set `tools/ui_capture.cfg` › `[web] base_url` to its dev server on this machine (and `start_command` if capture should start it). Leave it empty for a native Flutter, mobile or desktop app.
3. To capture, install Node 18 or newer if it isn't there, then once per clone: `cd tools/ui && npm install && npx playwright install chromium`. The check doesn't need it.
4. Replace the seed's root-route entry in `tools/ui/screens.mjs` with one entry per screen the app has (see `.app-director/procedures/ui-design.md` › The catalog), or leave it for the next item that touches a screen. Run `bash tools/ui_capture.sh --missing` (onboarding does this on an upgrade and reports; it never fails) to list the screen files the catalog doesn't cover.
5. Add `product/ui/` and `tools/ui/` to the Layout table in your AGENTS.md (the template's rows: screen specs and `captures/` (gitignored), the director's drawings in `director/ui/`; screen capture, with `screens.mjs` the catalog). If you want to design screens by drawing, add the row `UI / screen layout` to Ownership as `director designs (director/ui/), agent builds`, and create `director/ui/`.
6. The capture tools pass ESLint's recommended rules. If the app's own ESLint rules report findings in `tools/ui/` (`eslint .` lints every folder), add `tools/ui/` to its ignores: they are framework files, not app code.
7. `.claude/settings.json` and the procedures `build.md`, `review.md`, `acceptance.md`, `align.md` and `design.md` are framework-owned: if you edited one, merge its `.adir-new` file. Restart Claude Code so the `/ui-design` skill and the changed settings load.

- **The README starts with the product brief.** The Install section opens with a "Start here" step: write your product brief in your own words first, from the template at the latest release, then install, and onboarding reads it and asks only what you left open. The template's header links to the latest template too, so a copied file explains itself. The selftest checks that both links point at the release tag `v<VERSION>`.
  - **Upgrade steps:** none. The README belongs to the App Director repository, and the template is a seed that's copied once and never overwritten.
- **Sessions that build at the same time each get their own git worktree.** The sessions rule in `rules.md` now applies to any two sessions that build, not only design and coding, and says why: a shared checkout lets one session's half-written files fail the other's check and Stop hook, and both queue on the same build artefacts. The commands stay the same (`git worktree add`, then `bash tools/setup-clone.sh` there). The README's day-to-day section points to the rule, and the selftest checks that it names the rule and its reason.
  - **Upgrade steps:** none. The rules file is framework-owned and arrives on upgrade.
- **Every subagent launch passes its model explicitly.** The builder, the reviewer, the researcher and an escalated retry each get the model for the item's size from the sizing table, set in the launch. Where the table has no entry for the size, or model sizing is off, the session model is passed the same way. No launch leaves a subagent to inherit the session's model, so the model a build runs on is always the one its launch names. `rules.md` states the rule, `next-task.md` applies it at each launch, and the selftest checks the wording.
  - **Upgrade steps:** none. The procedures and rules are framework-owned and arrive on upgrade.

## 1.7.1 (2026-10-18)

- **An install from a development snapshot says so.** An install from a source whose `CHANGELOG.md` has entries under `## Unreleased` records `# app-director <version> + unreleased (<commit>)` as the manifest's first line, and its closing lines say it is a development snapshot, not a release, with where the latest release is listed. `VERSION` stays at the last release until a release is cut, so the manifest tells the truth. The commit comes from the source's git checkout (a release zip has none) and goes on a `# source <commit>` line, which release installs get too. An install from a release records the plain version. Upgrades read the old version without the suffix, so an upgrade from a snapshot works.
