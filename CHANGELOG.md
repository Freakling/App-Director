# Changelog

Each entry lists what changed. **Upgrade steps** at the end of an entry cover both framework fixes and app-owned file updates (AGENTS.md, TASKS.md, product/brief.md), so every project reaches the same capability level after upgrading. Onboarding carries them out; the fast upgrade mode runs only these steps, and the full mode also re-checks everything as if newly installed.

## Unreleased

- **Claude Code records the human's approval of a summary, and stops record writes no approval covers.** In an app, the human left a question dialog unanswered and typed a complaint instead; the dialog's tool result told the assistant to treat that message as the answer, and it wrote a decision line, brief text and a `todo` item. The commit now refuses them (below); these hooks act earlier. `record-approval.sh` (new) records the approval itself, from the human's own message, with `bash tools/records.sh approve <id> --hook`: a message that is nothing but one of `[approval] words` (with one `.` or `!`, and optionally the summary's id, `ok S7`) approves the summary this session registered since the human's previous message, or the one named; in a question dialog, the Approve option of a question that names the summary does. A bare word with no summary of this session registered since the human's previous message is an ordinary message ("yes" to "Shall I run the tests?"). When that previous message alone passed over a summary of this session that is still unapproved (the human asked about it, got an answer, and now writes "ok"), the assistant is also told that the word approves nothing, and to show the lines again and ask for the word with the id; a summary two messages have passed over is forgotten. An ordinary message, and a dialog whose answers approve no named summary (a dialog that approves one withdraws nothing, whatever its other answers say), withdraws the approvals of this session's summaries not yet committed. While nothing of this session is registered or approved it prints nothing and starts no process; otherwise it starts one `records.sh withdraw` when an approval is open, and tells the assistant, for each summary withdrawn or registered since the previous message, that nothing of it may be written. A message is read only as far as its first bytes (64 KB of input at most), so a long pasted one costs no more than a short one, and is never an approval; a prompt whose `session_id` isn't in that window withdraws every open approval. An approval counts only in the session that registered the summary (`record-watch.sh` stamps a summary only from the response of the call that ran `records.sh summary`, by the id and the hash in it, every such line in it, and tells the assistant when that output didn't come back, a redirect say), never for a subagent's summary, and never from a framed message (a subagent's report, another session's message) or a prompt the session scheduled; scheduling or sending a prompt that is only an approval word is refused. `record-watch.sh` (new) tells the assistant at once, after a file tool or a shell command, which record lines no approval covers, whatever wrote them (`sed -i`, a `node -e` or `python -c` one-liner, a redirect), once per list, and what to do either way, since it can't know who wrote them: lines the assistant wrote come out again or go into a summary for the human's approval, and lines the human wrote stay, for the human to commit after `bash tools/records.sh approve --staged` in their own terminal; a subagent is told it never writes records. `guard-protected.sh` now refuses a write to the brief or the decisions without an open approval (always from a subagent) and any write under `.app-director/state/records/`, and runs for MultiEdit and NotebookEdit too. While `tools/check.cfg` differs from the last commit, the watch saves the last commit's record paths, which the commit gate reads, and both hooks guard those as well as the working copy's, so moving `brief` in an uncommitted `tools/check.cfg` doesn't unguard `product/brief.md`. The defaults (`product/brief.md`, `product/decisions.md`, and for the watch the stories, the tasks and `tools/check.cfg`) are guarded always, so a `tools/check.cfg` changed where the watch didn't see it can't unguard them. Both read a path the same way (`.claude/hooks/record-paths.sh`, new, sourced by both): case-insensitively on Windows, macOS and a Windows drive under WSL (`/mnt/<letter>/`), without a `\\?\` prefix, and on Windows without a segment's trailing dots and spaces. On Windows the file guard refuses a path with a stream (`decisions.md::$DATA`) or an 8.3 short name (`DECISI~1.MD`), and the watch treats one as a possible record file. Both read their input only as far as they need it (the first 64 KB, on to the path when it isn't there), and drain the rest. The watch's git commands and the check it runs use `GIT_OPTIONAL_LOCKS=0`, so they never take a lock another session's commit needs. It stores the approvals and, per session, the summary counter at the previous message and the scheduled prompts: never a message's text. What the hooks receive, from a probe in the Claude desktop app's Code tab on Windows: a typed message (and a button of the next-step box) is `UserPromptSubmit`, sometimes with `<system-reminder>` blocks in front; a dialog's answer fires no `UserPromptSubmit`, but `PostToolUse` on `AskUserQuestion` carries `tool_response.answers`, and a message typed while a dialog is open gives the answer "[User did not answer this question..." and then a `UserPromptSubmit`; a subagent's report and another session's message arrive framed (`<agent-message`, `<cross-session-message`); a scheduled prompt arrives as plain text with nothing to tell it from a typed one, and the `Stop` input lists the pending ones (`session_crons`); a subagent's tool calls carry `agent_id`. Limits: a hook can't see whether the assistant showed the human the summary's lines (`Stop` has the last message only when a turn ends with text); an approval forged on purpose from the same account can't be ruled out; the terminal and the IDE extensions weren't probed.
  - **Upgrade steps:** the hooks and `.claude/settings.json` are framework-owned and arrive with the upgrade. If the app changed its `.claude/settings.json`, the installer keeps it and writes `.claude/settings.json.adir-new` beside it: merge the new wiring from it (`UserPromptSubmit` and a second `Stop` hook for `record-approval.sh`, `PreToolUse` for `MultiEdit|NotebookEdit` and for the tools that carry a prompt, `PostToolUse` for `AskUserQuestion`, `record-watch.sh` on `PostToolUse` and `PostToolUseFailure`) and the `bash tools/records.sh` allow and deny rules, then delete it. Nothing else in an app's own files changes; `[approval] words` in `tools/check.cfg` is already there.
- **The command guard keeps approvals the human's, and refuses the git commands that commit past the record gate.** In a segment of a command that has a word ending in `records.sh`, in the forms the guard can read (it reads the command's words, quotes removed, and a heredoc body a shell runs), the word after it must be one an assistant runs (`summary`, `check`, `trailer`, `status`, `report`, `word`, `open`, `withdraw`), whatever runs it (`bash`, `zsh`, `env`, `nice`, `timeout`, `xargs`): `approve`, any other word and no word at all (`... | xargs bash tools/records.sh`) are refused, and so is a segment with a `$`, a backtick or a glob in its words (a `records.sh` command is written out literally). A segment whose command only reads or copies files (`cat`, `head`, `tail`, `less`, `grep`, `rg`, `git`, `diff`, `chmod`, `ls`, `wc`, `awk`, `cp`, `sed -n`, `bash -n`) passes. A word that is a path into `.app-director/state/records` is refused; in a search (`grep`, `rg`, `git grep`) only the last word is read as a path. `git cherry-pick`, `git revert`, `git rebase` and `git am` are refused where git is the command being run (`git -C x revert`, `git -c k=v rebase`, `env ... git am`, `timeout 60 git rebase`): they make commits without the pre-commit hook, so the human runs them. The guard doesn't read them run through `xargs` (`... | xargs git rebase`) or after a `timeout` option that takes a value (`timeout -s KILL 60 git rebase`). A message, a title or a search that names any of these (`git commit -m "..."`, `gh pr create --title "..."`, `grep -rn "git rebase"`, `grep -n 'withdraw$' tools/records.sh`) is no such command and passes. A bash script path under `tools/` with a glob in it is refused too. `settings.json` denies `bash tools/records.sh approve*` and allows `summary`, `check`, `trailer`, `status` and `report`.
  - **Upgrade steps:** none beyond the `.claude/settings.json` merge above; the hook is framework-owned and arrives with the upgrade.
- **`tools/records.sh` has `word <word>` and `withdraw <id>...`, and reads only inside the repository.** `word` says whether a word is one of `[approval] words`, as `approve` matches it; `withdraw` with ids withdraws only those summaries' approvals. A summary file outside the repository is refused (an error quotes its lines), and so is a `report` argument that starts with `-` (git would read it as an option). `summary` claims its id with `mkdir` of a lock, so two runs at once never share one, writes the summary's files before the counter moves (never back), so a reader never sees an id whose files aren't there yet, and takes a Windows-form path inside the repository (`C:/...` against a working folder `/c/...`).
  - **Upgrade steps:** none; `tools/records.sh` is framework-owned and arrives with the upgrade.

- **A commit refuses record lines the human hasn't approved.** The rules said nothing is written to the records without an approved summary, and an assistant wrote decision lines, brief text and `todo` items and committed them all the same: prose didn't hold, so the commit now refuses. `bash tools/records.sh summary <file>` registers the exact lines a summary adds and removes, per file, and prints its id (`S<n>`), the first 12 characters of its hash and the lines, to be shown to the human word for word. The human's approval is recorded against that hash: `bash tools/records.sh approve <id>` in their own terminal (it refuses without one, so an assistant's shell can't run it), or through an assistant adapter's own hook (`approve <id> --hook`, which the adapter must keep the assistant from running). The pre-commit hook runs `bash tools/records.sh check` before the check: a staged line added to or removed from the brief or the decisions, a confirmed story or a changed Last validated line, every line but `Note:` of an item added or moved on that isn't `proposed` (unless `[records] bugs` frees the bug: under `cited`, its `Brief:` names a heading of the brief outside Open Questions, each part of a path under the one before, or its `Stories:` names a confirmed story's exact ID), a changed `Done when`, `Repro` or `Question`, an item moved back to `proposed` or removed before it's `done`, and a change to `[records]` or `[approval]` in `tools/check.cfg` all need an approval that has exactly that line. In the brief and the stories a line is placed by the path of headings above it, so an open question moved into a flow, or a confirmed story moved to another table, needs an approval of its `- ` and its `+ ` line. A plain rename (one heading changed, at the same place and level) needs only the heading's own two lines; any other change to the headings (a heading added, removed or re-levelled, or two changed) lists every line it re-homes, so restructuring the brief puts each moved line in the summary. A heading is `#` to `######` after up to three spaces, or a setext heading. An approval binds a line's file and text, not its place. An item heading is any heading whose text starts with an item ID; it reads `ID · title · status · size · owner` as `.app-director/tasks.md` gives it (a bug adds its severity), or the older `ID · title · size · status`, and one that reads neither way counts as not `proposed`. An item runs to the next item heading or heading of level 1 or 2, and fields are found in any common form (`* Done when:`, `- **Done when:**`, indented, with continuation lines). Approvals apply whole: the largest first, each whose lines are all in the commit takes them, one summary line per line of the commit, and any other covers nothing in that commit. The refusal names each line, the heading it sits under, why it's protected and what to do, and why an approval doesn't cover it (the text differs from the summary, withdrawn, older than its summary, already used in a commit, or its lines already committed). Status changes, the escalation label, `Note:` and `PRs:` lines, `Next IDs`, pruned `done` items, moved items, `unconfirmed` stories and `proposed` items pass, and so do the lines a merge brings from a parent: during a merge the index is judged against HEAD, and a change is free only as often as another parent brought it, that is, as often as the same change (file, sign and text; a removed item by its ID) is in that parent against each of its merge bases with HEAD. With no common ancestor, or when the other commit is an ancestor of HEAD, nothing is free. An item renumbered while resolving a duplicate ID is a record change, and `.app-director/tasks.md` › Merge conflicts says so. A new `commit-msg` hook asks the commit that uses an approval to name it, `Approved: <id> <date> "<word>" <hash>` (`bash tools/records.sh trailer` prints the line); once that commit is in the history, or the approval's lines are already committed, the approval covers nothing more, so no log of the human's messages is kept and `product/decisions.md` keeps its format. The hash covers the summary's id and registration time with its text, so the same text registered again can be approved again. While the install manifest lists `tools/records.sh`, both hooks refuse a commit when it is missing, and say how to restore it. `bash tools/records.sh withdraw`, `status` and `open <path>` are there for an adapter's hooks, and `report [<since>]` lists the approvals used and the `proposed` items. The state is in `.app-director/state/records/`, which git ignores. Its limits: the gate judges commits made with `git commit`, and commands that make commits without running the pre-commit hook (`git cherry-pick`, `git revert`, `git rebase`, `git am`), a commit made with `--no-verify` and a prototype checkout aren't judged, nor is a merge `git merge` or `git pull` completes by itself, which runs no pre-commit hook (whatever `-X theirs` or a `merge=union` attribute chose passes); a merge trusts the commits it brings, so lines in a commit made without the hooks (a stash, for one) pass when it is merged; an approval forged on purpose from the same account can't be ruled out, since the state lives in the working copy.
  - **Upgrade steps:** run `bash tools/setup-clone.sh` in each clone, so the new `commit-msg` hook is installed beside the other two (the pre-commit gate works without it, but then no commit names its approval, and an approval stays open after its commit). `tools/check.cfg` is project-owned and kept: the `[records]` paths (`brief = product/brief.md`, `decisions = product/decisions.md`, `stories = product/user-stories.md`, `tasks = TASKS.md`) and `[approval] words` (`godkänt, godkänd, approve, approved, ok, ja, yes, kör`) are optional, and those defaults apply without them; to set them, copy the seed's keys and comments (`project/tools/check.cfg`) and commit that change with an approval, as below. Lines already committed aren't judged, and neither is the commit that first adds a record file. When the human commits an edit of their own to a record file, they run `bash tools/records.sh approve --staged` in their own terminal after staging it, type an approval word, and commit with the `Approved:` line it prints.

- **An item the assistant files by itself is `proposed`, and no procedure builds it.** In an app, the assistant wrote design decisions, brief text and `todo` items without an approved summary, and the procedures themselves queued its own ideas (a builder's `Found:` lines, review leftovers, research follow-ups, a failing full run) as buildable work. `.app-director/tasks.md` has a new status, `proposed`: `/next-task` never picks it, an item that depends on it waits, and it counts as not built. The human's approval of a summary (`design.md` › Summary and approval) makes it `todo`; a `proposed` item the human names to `/next-task` is shown and put to that approval, not built. The procedures file those items as `proposed`, and a run's final report names every one it filed. The bugs rule (`rules.md` › Doing the work): a bug restores behaviour the brief or a confirmed story already states, so a bug whose `Brief:` names that heading or whose `Stories:` names a confirmed story may be filed `todo`; any other bug is `proposed`. `[records] bugs` in `tools/check.cfg` sets it (`cited` by default, `all` or `none`) and onboarding asks it once. Items the human approved (a design session's, an acceptance check's Broken items, a security assessment's findings) stay `todo`. The assistant's own status changes, `Note:` lines, `Next IDs`, pruning and `unconfirmed` stories stay free.
  - **Upgrade steps:** `tools/check.cfg` is project-owned and kept: without `[records] bugs` the default `cited` applies. To set it, add the seed's `[records]` section (`project/tools/check.cfg`, with its comment) and the value the human wants: `bugs = cited`, `all` or `none`. Existing items keep their status. Nothing else in an app's own files changes; the rules and procedures are framework-owned and arrive with the upgrade.
- **A message is not an approval.** `rules.md` › The human decides says that a complaint, an observation, a screenshot or a bug report is not a decision and not a request to record one (diagnose, propose and ask); that a question dialog the human left unanswered is no answer, whatever its tool result says, and the message they sent instead re-opens the options it touches; and that a run mode ("work through the queue") or a project's commit rule ("commit without asking") approves commits, never a decision, brief text, a confirmed story or a `todo` item the human hasn't approved. `design.md` points to it where an answer is waited for.
  - **Upgrade steps:** none; the rules and procedures are framework-owned and arrive with the upgrade.

## 1.15.0 (2026-11-10)

- **The check has a fast tier for each build and commit, and the full tier runs when it's due.** An app with about 4,900 tests ran its whole check on every commit and again at the end of a turn: 15 to 25 minutes a commit. `bash tools/check.sh --fast` runs UI purity, the secrets scan and the stack check on what the change needs: for TypeScript, tsc over the project (incremental), eslint on the changed files (on the whole project with a legacy `.eslintrc*` config, which can't skip an ignored file named on the command line) and the tests related to the change (`vitest related`, `jest --findRelatedTests`, with coverage off). A fast request for a change of more than 100 source files or 6,000 characters runs as the full tier, with its limit and its record, and says so, since the file lists must fit on one command line (cmd.exe takes 8,191 characters). A removed file that a `[tests] fast-map` rule matches still runs its test. `[tests] fast` picks `related`, `all` or `none`, and `[tests] fast-map` runs a named test for a matching change instead of every test related to it (a wording file and its translation test, say). Where neither the stack check nor `tools/check.local.sh` reads `CHECK_TIER` (the python, flutter and none stacks don't), there is one suite: a fast request runs as the full tier, with its limit and its record, and says so, and that one pass stands for a build, a commit and a push alike. `bash tools/check.sh` is still the full tier: every step over the whole project. `bash tools/check.sh --due` says whether the full tier is due: no full pass recorded yet, `[tests] full-every` commits since the last one (10 by default), or a changed dependency, toolchain setting, file under `tools/` or `[tests] full-when` path. The builder verifies with the fast tier (`build.md` step 6); the hooks pick the tier (below); a run of several items ends with one full run, and a failure there becomes a bug item; and a release runs the full tier. `rules.md` › Done and Running the check say which tier runs where. Each tier has its own time limit, `[tests] timeout-fast` (300 s by default) and `timeout-full` (3600 s; the older `timeout` counts when it isn't set). A long run prints its minutes every 60 s, on a line of its own, and a run past its limit says to run it again in the background with a longer `CHECK_TIMEOUT` (a commit reuses that pass) or to raise the setting. `tools/check.local.sh` gets `CHECK_TIER` and, in the fast tier, `CHECK_CHANGED`, so it can leave its own slow steps to the full tier. `[tests] workers` sets vitest's `--maxWorkers`, and a full run lists the ten slowest test files.
  - **Upgrade steps:** `tools/check.cfg` is project-owned and kept: without the new keys the defaults apply, and the old `timeout` still works as the full tier's limit. To set them, put the seed's `[tests]` section (`project/tools/check.cfg`, each key with its comment) in place of the app's, or add it when there is none, keeping the app's `timeout` value as `timeout-full` (3600 when it had none): `timeout-fast = 300`, `timeout-full`, `fast = related`, `full-every = 10`, and `full-when`, `fast-map`, `ignore` and `workers` empty. If `tools/check.local.sh` has slow steps (a production build, say), skip them when `CHECK_TIER` is `fast`; the full tier still runs them. An app where neither the stack check nor `tools/check.local.sh` reads `CHECK_TIER` needs nothing here: it has one suite, which a fast request runs as the full tier. Nothing else: the rules, the procedures, `tools/check.sh` and the stack scripts are framework-owned and arrive with the upgrade.
- **A recorded result says what it stands for, and a miss says what changed.** A builder's pass ran again in the commit hook, and the cache missed without saying why. A recorded result (`.app-director/state/last-pass` or `last-fail`) now carries its tier, time, commit and caller, with a list of its files and their hashes beside it. A fast pass never stands for a full one. It checks the changes from HEAD, so on another commit it stands for a fast request only when every path that differs from HEAD now was among those it checked: once the commit hook's pass is committed, the Stop hook and the next item's check reuse it, while a reset that leaves more changed runs again. A reuse names the pass it repeats, and every miss names what changed since the result it compared with: `src/x.ts and 3 more changed`, a new or removed file, another gitleaks version, a fast pass for a full request or on another commit, or a result recorded by an older check. `[tests] ignore` leaves paths that can't change a result out of the cache and of the fast tier's changed files, and a commit that stages only those starts no check. The paths that make the full tier due count like source files: a change to a dependency or its lockfile, a toolchain setting, a file under `tools/` or a `[tests] full-when` path (a migration, say) is never reused from the cache, and a commit that stages nothing else still starts the check. Which paths count is `tools/check.sh`'s one rule, which the pre-commit hook asks for. Every run and reuse is a line in `.app-director/state/check-runs.log` (it keeps its last 500 lines once it passes 1000), and every run ends with a summary: its tier, result and time, each step's seconds, the tests run, the cache's note and what it left to the full tier.
  - **Upgrade steps:** none; `tools/check.sh` is framework-owned and arrives with the upgrade. A result recorded by the older check has no tier, so the first `--if-changed` check after the upgrade runs, and says why.
- **One check runs at a time in a checkout, and the hooks pick the tier.** A Stop hook's check beside a commit hook's ran a second suite and timed both out. A run of either tier holds `.app-director/state/check.lock`; another check says which run it waits for, and reuses that run's result, pass or fail, when the files and the tier match, instead of starting a second suite. The running check touches its own lock every minute, and the lock names its time limit. A lock is removed, with a note, when its process is gone; when no one has touched it for 5 minutes at two looks at least 75 s apart, so a reused pid can't hold it and a machine waking from sleep keeps a live one; or when it is older than twice the longer of its holder's limit and the waiter's, plus 600 s. A lock another run took in the meantime is put back. After a wait the check reads HEAD again, and `CHECK_WAIT` caps the wait (`check: busy:`, exit 3). The pre-commit hook runs the full tier when `--due` says so and the fast tier otherwise, says which and why, reuses a builder's pass on the same files, notes a staged file that also has unstaged changes, and on exit 3 says nothing was committed and how to go on; the staged secrets scan still runs on every commit. Before a commit the agent asks `bash tools/check.sh --due` and, when the full tier is due, runs `bash tools/check.sh --if-changed` in the background first: the hook reuses that pass, so the full run never sits inside the commit command, where a tool's time limit would cut it short (`rules.md` › Running the check). The pre-push hook now runs the full tier after its prototype refusal, reusing a full pass of the same files, unless the push only deletes refs; a failure, or a check that can't run, blocks the push. The Stop hook runs only the fast tier, never in a repository with no commit yet, and waits no longer than the fast tier's limit for another check, then ends the turn quietly, since the running check gates the commit; a check that couldn't run is reported as unverified, not failed. `selftest.sh` covers the tiers, a stack with no fast mode, `--due`, the paths that count, the cache's notes, the run log, the time limits, the lock and the hooks.
  - **Upgrade steps:** none; the hooks are framework-owned and arrive with the upgrade. A push now runs the full tier, so in an app with a long suite, run `bash tools/check.sh --if-changed` in the background before pushing: the push reuses its pass.
- **Reading `tools/check.cfg` starts no process, whatever its line endings.** A settings file checked out with CRLF line endings sent every line through a pipeline (a line with a comment after its value went through one too): several seconds for each call of the check on Windows, and a commit calls it three times. The carriage return and the comment are now cut in bash. In an app whose settings have CRLF line endings, `bash tools/check.sh --due` went from about 6 s to about 1 s, and `bash tools/check.sh --fingerprint` from 7 to 9 s to under 3 s.
  - **Upgrade steps:** none; `tools/check.sh` is framework-owned and arrives with the upgrade.

## 1.14.2 (2026-11-05)

## 1.14.1 (2026-11-05)

- **The guard blocks a Python with nothing to run.** `python3 -`, `python` or `py -3` with no script, no `-c`, no `-m` and nothing fed to it waits for input that never comes, and a time limit doesn't change that.   - **Upgrade steps:** none; the hook is framework-owned and arrives with the upgrade.

The guard cases source the hook in a subshell of one bash per lane instead of starting a bash on it each time, one grep looks for a message across its cases, plain text in a source file is found without a process, and a copy leaves out the `.git` and `node_modules` a case doesn't use.   - **Upgrade steps:** none; `selftest.sh` is this repository's own and isn't installed into apps.

  - **Upgrade steps:** none; `tools/check.sh` is framework-owned and arrives with the upgrade.

## 1.0.0 (2026-10-05)

Initial public release.

- **Claude Code plugin.** A `.claude-plugin/plugin.json` manifest makes App Director a first-class Claude Code plugin, installable from the marketplace with `/plugin install app-director`. `skills/app-director/SKILL.md` is the bootstrap skill; a root `SKILL.md` covers the standalone `~/.claude/skills/` use case. `package.json` enables npm/npx distribution.
- **Protected workspace (`director/`).** The human's personal space: mockups, brand assets, reference images, notes, third-party API specs. The agent reads files there for context but is blocked from creating, modifying or deleting anything inside it. Edit and Write tool hooks enforce this in Claude Code.
- **Ownership interview in onboarding.** Step 8 goes through every work area (frontend, business logic, backend, database schema, visual design, copy, testing, infrastructure) and asks who owns each. Human-owned areas get a documented placeholder policy. AGENTS.md has an `## Ownership` table to record the result.
- **Full workflow.** Design sessions, build-check-commit loop, acceptance checks, alignment pass, archive, release: each as a skill command in Claude Code.
